# Производительность v8Unpack: ревью кода и план работ

Ревью кода `src/` версии 3.0.55 с замерами `perf` на реальной большой конфигурации.
Измерено на VPS (2 ядра, 4.4 ГБ RAM, ext4), Ubuntu 24.04.

## Что уже сделано (3.0.56)

Первый этап плана выполнен, поведение не изменилось — сборка mods, конфигурации со справкой
и расширения даёт прежние sha256, круг на расширении расходится только во времени манифеста:

- A3 — чтение блока в поток: переиспользуемый буфер 1 МБ вместо `new char[1024]` на вызов;
- A4, A5 — выравнивание блока и резерв заголовка TOC пишутся одним `write` вместо побайтового
  вывода потока;
- A7 — тип элемента берётся у записи каталога (минус один `stat` на члена), созданные каталоги
  кэшируются: `create_directories` больше не проверяет цепочку родителей на каждом члене;
- B1 — `CV8File::GetData` обходит элементы по ссылке (была полная копия данных каждого члена);
- B5 (частично) — `extractFormModules` читает только начало файла для отбора описаний форм:
  раньше читался каждый файл целиком;
- B8 — буферы `Deflate`/`Inflate` освобождаются `free()` (были выделены `realloc`);
- C3 — ключ `--timings` печатает время сжатия и распаковки.

`statx` в сборке сократились с 4019 до 2978 на конфигурации из 403 членов. Остальное —
этапы 2 и 3 ниже.

## Как измеряли

```
perf record -F 300 -g -- /usr/bin/time -v ./v8unpack -CO <дерево BP> out.cf
perf record -F 300 -g -- /usr/bin/time -v ./v8unpack -DE 1Cv8_bp.cf <дерево>
```

Материал: дерево BP — 86 046 файлов, 3.7 ГБ, манифест на 78 844 записи, 2.83 ГБ данных;
контейнер BP — 762 МБ. Замеры под `perf` идут медленнее (сэмплирование с размоткой стека):
`-CO` 13:20 под perf против ~10:20 без неё, `-DE` 7:22 против ~6:10.

Кроме профиля, считали системные вызовы: `strace -c -f ./v8unpack -CO|-DE …` на конфигурации
из 403 членов (450 файлов) — 4019 `statx` на сборке и 15 026 на распаковке.

| | `-CO` (сборка) | `-DE` (распаковка) |
|---|---|---|
| wall | 13:20 (perf) | 7:22 (perf) |
| CPU процесса | user 298 c + sys 57 c | — |
| занятость CPU | **44 %** (0.88 ядра из 2) | **44 %** |
| RSS | 205 МБ | 423 МБ |
| чтение / запись | 4.2 ГБ / 2.3 ГБ | 6.5 ГБ / 5.4 ГБ |
| minor page faults | 82 382 | 303 603 |

Главный вывод: **оба направления упираются в диск, а больше половины времени второе ядро
простаивает.** Эффективная скорость диска здесь ~9–10 МБ/с на записи, ~27 МБ/с на чтении
вперемешку с записью.

## Что показал профиль

### `-CO` (сборка): zlib 76 % циклов, но половина времени — ожидание диска

| доля сэмплов | символ |
|---|---|
| 76.4 % | `deflate` (zlib): 69.8 % — `Deflate(char const*, char**, …)` (в память), 8.0 % — `Deflate(istream&, ostream&)` (через временный файл) |
| 6.5 % | `StructuredPacker::packFromManifest()` |
| 5.2 % | `recursive_pack<Format16>()` |
| ~11 % | системные вызовы (`entry_SYSCALL_64`) |

То есть из 298 c пользовательского времени ~227 c — это zlib, остальное — обход дерева,
сериализация вложенных контейнеров и системные вызовы. При 44 % занятости CPU ~500 c ушло
на ожидание ввода-вывода.

### `-DE` (распаковка): 46 % сэмплов — в ядре, zlib почти не при чём

| доля сэмплов | символ |
|---|---|
| 41 % | `entry_SYSCALL_64` (ядро) |
| 18.9 % | `QIODevice::readAll()` |
| 16.2 % | `StructuredUnpacker::extractFormModules()` |
| 13.6 % | путь `read()` в ext4 (`vfs_read` → `ext4_file_read_iter` → `filemap_read`) |
| 10.7 % | `malloc` / `_int_malloc` |
| 9.2 % | `statx` |
| 8.3 % | `QString::append(QChar)` |
| 7.4 % | `parse_1Ctext()` |
| 6.6 % | `libz` (inflate) |

Здесь сжатие не при чём: распаковка дешева. Всё решает объём системных вызовов, чтение
файлов целиком, побайтовая сборка строк и аллокации на каждый член.

## Найденное в коде

### A. Основное

**A1. Всё однопоточно, второе ядро простаивает.** Ни сжатие, ни обход членов не
распараллелены, занятость CPU 44 %. Члены контейнера независимы, поэтому схема «N потоков
сжимают/распаковывают в буферы, один пишет результат в исходном порядке» даёт до 1.6–1.8×:
сжатие уезжает на второе ядро и перекрывается с диском. Требования: сохранить порядок
записи и байтовую идентичность результата, аккуратно обработать ошибки одного члена.

**A2. `-CO` строит дерево-двойник во временном каталоге.** `StructuredPacker::run()`
материализует всё дерево в `m_tempDir` (жёсткими ссылками — это уже сделано) и только потом
вызывает `recursive_pack` (`src/V8File.cpp:1195`). Ссылки убрали копирование байт, но
остаются 86 046 лишних записей каталога, двойной обход дерева и двойное место на диске под
крупные конфигурации. Правильное направление — писать контейнер прямо по манифесту.

**A3. Чтение блока через буфер 1 КБ с аллокацией на вызов.**
`src/V8File.cpp:178`: `const int buf_size = 1024; char *pBlockData = new char[buf_size];`.
Используется при распаковке в поток (`-U`). На 78 844 членов это десятки тысяч мелких
записей и столько же `new/delete[]`. Нужен один переиспользуемый буфер 1–4 МБ.

**A4. Выравнивание блока пишется по одному байту.**
`src/V8File.cpp:289-292, 308-312, 327-331, 357-361`: `for (…) file_out << '\0';` —
побайтовый вывод через поток. Крупная доля членов BP меньше 4 КБ, то есть выравнивание до
страницы идёт на каждом. Нужен один `write()` нулевого буфера.

**A5. Резерв заголовка в `recursive_pack` — тоже побайтово.** `src/V8File.cpp:1093-1095`:
цикл на `cur_block_addr` байт, для BP это ~950 КБ.

**A6. Крупные члены упаковываются через временный файл в `/tmp`.**
`src/V8File.cpp:1150-1155`: `Deflate(file_in, tmp_path)` → `SaveBlockData(…, tmp_file_path)` →
`remove(tmp_path)`. Порог — `SmartUnpackedLimit` = 20 МБ (`src/V8File.cpp:416`), у BP таких
членов 7 (244 МБ), плюс все 264 члена от 1 до 20 МБ идут через память целиком (729 МБ).
Двойная запись и чтение заменяются потоковой записью с патчем заголовка блока.

**A7. Много лишних `stat` — самая дорогая мелочь.** 9.2 % сэмплов в `statx`; `strace -c`
на конфигурации из 403 членов (450 файлов) показывает **4019 `statx` на сборке** и
**15 026 на распаковке** — это ~10 и ~37 обращений к индексам на каждый член, 28 % и 50 %
времени системных вызовов соответственно. Каждое обращение на медленном диске — десятки
микросекунд, и на 78 844 членах это десятки секунд.

Источники: при обходе каталога для каждого элемента вызывается свободная функция
`boost::filesystem::is_directory(path)` (`src/V8File.cpp:1118`) вместо типа, который уже
знает запись каталога, и сразу за ней `file_size()`; в `StructuredPacker` — `QFileInfo` на
каждый элемент манифеста и на каждую ссылку/копию; в `StructuredUnpacker` — `QFileInfo`
на каждый член, причём на нескольких проходах. Нужно: брать тип из записи каталога,
не проверять существование только что созданных путей, кэшировать результаты обхода.

### B. Среднее

**B1. `CV8File::GetData` копирует элементы по значению.** `src/V8File.cpp:1346` —
`for (auto elem : Elems)` (на строке 1323 тот же список обходится по константной ссылке).
Копируется `vector<char> data` каждого члена — полное дублирование данных контейнера.

**B2. Сжатие и распаковка собирают результат в буфер 16 КБ с копированием.**
`src/utils.cpp:299-357` (`Inflate`) и `:359-413` (`Deflate`): рост `realloc` шагами по
`CHUNK` плюс `memcpy` из стекового буфера в приёмник. Можно писать прямо в приёмник,
верхнюю границу даёт `deflateBound()`.

**B3. Лишний `memcpy` при упаковке члена.** `src/V8File.cpp:1257-1258, 1278-1279`:
сжатые данные копируются из буфера zlib в `data` (это уже третья копия с учётом B2).

**B4. Побайтовая сборка строк в парсере.** `QString::append(QChar)` — 8.3 % сэмплов на
`-DE`, растёт из `parse_1Ctext` (7.4 %). Нужен `reserve()` и блочная вставка.

**B5. Чтение файлов целиком в `extractFormModules`.** 16.2 % сэмплов и основной вклад в
RSS 423 МБ: вместо чтения нужных диапазонов файл читается `readAll()` целиком.

**B6. Аллокации на каждый член.** `malloc`/`_int_malloc` 10.7 % и 303 603 minor page
faults: буферы не переиспользуются между членами.

**B7. Мелкие буферы у потоков контейнера.** `CHUNK = 16384` (`src/utils.cpp:13`) и потоки
без `pubsetbuf` — на медленном диске это лишние системные вызовы. 1–4 МБ дают меньше
переключений.

**B8. Несовместимая пара выделения и освобождения.** `Deflate`/`Inflate` получают буфер
через `realloc` (`src/utils.cpp:307, 367`), а вызывающий освобождает его `delete[]`
(`src/V8File.cpp:1260, 1281`) — формально UB. Нужен `free()` (или `malloc` в обе стороны).

**B9. Каталог обходится дважды.** `src/V8File.cpp:1057-1067` (подсчёт членов) и
`1099-1160` (запись) — можно за один проход.

### C. Гигиена

**C1.** `Format15` жёстко зашит в `CV8File::GetData` (`src/V8File.cpp:1293`) и
`LoadFileFromFolder` (`:1005`) — для Format16-вложенных контейнеров это неверно.
**C2.** Манифест пишется `Indented`-JSON: на BP ~15 МБ, читается и пишется целиком.
**C3.** Нет встроенного замера фаз. Отладочный ключ `--timings` (чтение, разбор
метаданных, сжатие, запись) дал бы возможность мерить без `perf`.
**C4.** Внешний ускоритель zlib: `zlib-ng`/`libdeflate` дают 2–3× на deflate, но это новая
зависимость и, главное, другой поток сжатия — байтовая совместимость с прежними сборками
теряется. Только как явная опция.

## План

**Этап 1 — дешёвые победы без изменения поведения (ожидаемо 10–20 %).**
A7 (убрать лишние `stat` — по замерам самые дорогие из мелких), A3 (буфер 1–4 МБ), A4 и A5
(запись выравнивания одним `write`), B1 (обход по ссылке), B8 (`free`), B9 (один обход
каталога), C3 (`--timings`).
Риск минимальный, байтовая идентичность сборки сохраняется. Проверка: эталоны
`1Cv8_mods.cf` = `5f035387…`, круг на `Спецификатор.cfe` (351 член), дерево BP.

**Этап 2 — убрать лишние копии и чтения (ещё ~10–15 %).**
A6 (потоковая упаковка крупных членов вместо временного файла), B2 и B3 (сжатие/распаковка
прямо в приёмник), B5 (читать диапазоны, а не файлы), B6 (переиспользовать буферы),
B4 (парсер без побайтового `append`), B7 (крупные буферы потоков).
Проверка та же плюс расхождение манифеста и дерева.

**Этап 3 — архитектурное (основной прирост, до 1.6–1.8× на 2 ядрах).**
A2 (сборка прямо по манифесту, без дерева-двойника) и A1 (конвейер «сжимаем параллельно —
пишем последовательно»). Это меняет структуру сборки, поэтому нужен отдельный этап
проверки: байтовая идентичность результата, порядок членов, поведение при ошибке одного
члена и при нехватке места.

**Отдельно, уже доступно.** `--level 6` (есть с 3.0.55) даёт −37 % времени сборки ценой
+1.15 % размера: 389.81 c против 619.86 c на BP. Для CI и внутренних сборок это готовый
рычаг; по умолчанию остаётся 9 ради байтовой совместимости.

## Чего делать не стоит

- Распараллеливать только zlib, не разобравшись с вводом-выводом: при занятости CPU 44 %
  выигрыш ограничен, пока диск ждёт.
- Переходить на `std::filesystem` ради «удобства» — в проекте принят Boost (и он тут
  ни при чём: `stat` дорог из-за количества вызовов, а не библиотеки).
- Менять уровень сжатия по умолчанию: от байтов зависит эталонный sha256 в CI.
