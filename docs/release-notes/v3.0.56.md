# v8Unpack 3.0.56

Меньше обращений к диску, меньше копий данных и мелких операций: сборка большой конфигурации
на тестовом сервере стала быстрее примерно на пятую часть. Формат контейнера и результат
сборки не изменились.

## Что ускорено

- **Распаковка читает только то, что нужно.** Отбор описаний форм раньше читал *каждый* файл
  контейнера целиком, чтобы проверить, начинается ли он с `{4,`. Теперь читается начало файла,
  а целиком — только настоящие описания форм. На тестовой конфигурации чтение с диска
  сократилось с 14.2 до 10.4 ГБ, процессорное время распаковки — на 10 %.
- **Меньше обращений к индексам файловой системы.** Каталоги проверялись на каждом члене:
  `create_directories` обходит всю цепочку родителей (в трассировке видно обращения к `/root`,
  `/root/workcpp`, …), а тип элемента запрашивался отдельным `stat`. Теперь тип берётся из записи
  каталога, а созданные каталоги запоминаются. На конфигурации из 403 членов число обращений
  к индексам при сборке сократилось с 4019 до 2978.
- **Меньше копий и мелких операций.** Выравнивание блоков и резерв заголовка таблицы адресов
  пишутся одним `write` вместо побайтового вывода потока; чтение блока использует
  переиспользуемый буфер 1 МБ вместо `new char[1024]` на каждый вызов; список элементов
  обходится без копирования данных каждого члена.
- **Корректность работы с памятью.** Буферы сжатия и распаковки, выделенные `realloc`,
  освобождаются `free()` (было `delete[]` — формально неопределённое поведение).

## Новый ключ

`--timings` печатает, сколько времени ушло на сжатие и распаковку:

```
$ v8unpack --timings -CO <дерево> <файл.cf>
Build `<файл.cf>` OK!
тайминги: сжатие 0.07 с (403 вызовов), распаковка 0 с (0 вызовов)
```

## Замеры на тестовом сервере

Дерево большой конфигурации: 86 046 файлов, 3.7 ГБ, 78 844 члена; контейнер 762 МБ; сервер с
двумя ядрами и медленным диском. Замеры сделаны подряд, прежним и новым бинарником, на одном
и том же дереве.

| | 3.0.55 | 3.0.56 |
|---|---|---|
| сборка контейнера | 10:45 | **8:21** |
| занятость процессора при сборке | 49 % | 59 % |
| чтение / запись при сборке | 9.5 / 4.8 ГБ | 9.1 / 4.8 ГБ |
| распаковка | 9:51 | 10:10 |
| чтение при распаковке | 14.2 ГБ | 10.4 ГБ |

Сборка быстрее из-за меньшего числа мелких операций. Распаковка на этом диске упирается в
запись (11.3 ГБ на дерево 3.7 ГБ), поэтому по времени не изменилась, хотя читает на четверть
меньше и тратит меньше процессорного времени. Что дальше — описано в `docs/PERFORMANCE.md`:
убрать промежуточные записи при распаковке и перекрыть сжатие с работой диска.

## Совместимость

Формат контейнера и раскладка дерева не менялись: сборка из того же дерева даёт байт-в-байт
тот же файл, `sha256` совпадает. Манифест остаётся версии 3, поэтому деревья нужно собирать
версией не старше той, которая их распаковала.

## Что проверено

- `1Cv8_mods.cf` — прежний эталон `5f035387…`;
- конфигурация со справочной информацией: 7 файлов `.html`, сборка `c253f04b…`;
- расширение со справкой: сборка `2b38c7ac…`;
- круг распаковка → сборка → распаковка на расширении — расхождений нет (кроме времени
  в манифесте);
- сборка большой конфигурации прежним и новым бинарником — файлы побайтово одинаковы
  (`14161894…`, 753 580 133 Б).
