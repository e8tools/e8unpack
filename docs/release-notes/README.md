# Описания релизов

Один файл на выпуск: `docs/release-notes/<тег>.md` — например `v3.0.48.md`.

Workflow `Release` публикует содержимое этого файла как описание релиза на GitHub.
Если файла для тега нет, описание собирается из истории коммитов (заголовки коммитов
от предыдущего тега плюс ссылка на `compare`). Черновой prerelease ветки
`release_develop` описания из этих файлов не берёт.

Что писать в описании (в порядке пользы для читателя):

1. Короткий заголовок-итог в одну строку — что меняется для пользователя.
2. **Что было не так / что нового** — по пунктам, с причинами, без пересказа диффа.
3. **Как это выглядит теперь** — примеры путей, команд, поведения.
4. **Совместимость** — что ломается, что нет (особенно если меняется раскладка каталогов
   или формат манифеста).
5. **Проверено** — на каких файлах гоняли `-DE`/`-CO`, что сравнивали, чем подтверждено.
6. **Файлы выпуска** — что лежит в каждом артефакте.
7. Ссылка на полный список изменений (`compare`).

Файл добавляется в коммит, на который ставится тег: сначала коммит с описанием, потом тег.
